    fix(plugin): harden i18n bundle — startup probe and per-key fallback
    
    GradumBundle trusted a hard-coded `messages.GradumBundle` resource
    path and exposed a single-line `message()` that delegated straight to
    DynamicBundle.getMessage. Two silent failure modes followed:
    
    1. If the resource itself was missing (renamed messages/ folder,
       wrong base name in a packaged plugin where the .properties got
       stripped by a buggy exclude rule), the first UI element that
       called `message()` would throw MissingResourceException. There
       was no log line tying the failure to the bundle path — the user
       would see empty labels in the tool window with no breadcrumb.
    
    2. If a single key was missing (typo, removed in zh_CN, never
       added in the first place), the same exception bubbled up, the
       Compose Text composable rendered empty, and "did I spell the
       key wrong?" was invisible unless you happened to have the IDE
       exception breakpoint on.
    
    This commit adds two defensive layers without re-architecting the
    resource layout (the hard-coded `messages.GradumBundle` path stays
    — the class lives in gradum.idea.bundle but its resources sit in
    the messages package on purpose, and moving 132 keys × 2 locales
    into gradum/idea/bundle/ is out of scope for a hardening fix):
    
    - `init {}` block on the object probes one well-known key
      (`gradum.toolwindow.welcome`) at class-init. If the resource is
      unreachable, a single WARN line in the IDE log names the bundle
      path and tells the user to check the .properties packaging.
    - `message()` now try-catches MissingResourceException, logs the
      offending key + bundle name at WARN, and returns `???<key>???` as
      the visible fallback. The UI is never blank, missing keys stand
      out in screenshots, and the log has the breadcrumb.
    
    `BUNDLE_NAME` and `PROBE_KEY` are kept as file-level `private const`
    because the supertype call `DynamicBundle(BUNDLE_NAME)` in the
    class header must resolve before any object-body initialiser runs,
    and Kotlin does not let a private const inside the object itself
    be referenced from its own supertype list. The file-level form is
    also slightly safer — it cannot accidentally be shadowed by an
    object member with the same name in a future refactor.
    
    No tests touched. No resource files moved.

    fix(plugin): make NDJSON parsing per-line resilient in GradumApiClient
    
    The previous `sendMessage` returned `Flow<String>` (raw NDJSON lines)
    and pushed the per-line JSON parse + try-catch onto the consumer in
    GradumChatSession. Two problems followed:
    
    1. The "do not let a malformed line kill the whole stream" guarantee
       lived in the consumer. Any new caller of `sendMessage` would have
       to remember to add the same per-line try-catch, or a single bad
       line (e.g. server sent a stray non-JSON byte mid-stream, or a
       serializer race) would tear the whole chat down. The user has hit
       this before in earlier sessions and it took a while to track down.
    
    2. The same JSON object was being parsed twice: once in the consumer
       to validate, once when dispatched into ChatEvent. Pure waste, and
       any future schema check would have to be added in two places.
    
    This commit moves parsing into GradumApiClient:
    
    - `sendMessage` now returns `Flow<JsonObject>` — every emission is a
      parsed, well-formed object. Lines that fail to parse are logged at
      WARN with line number + 200-char preview and skipped. Lines that
      parse but are not JSON objects are also skipped with a clear log.
    - Added a private `FlowCollector<JsonObject>.parseAndEmit(line, n)`
      extension so the per-line try-catch is in one place. A lineNumber
      counter makes log triage easier ("which event in the stream went
      bad?").
    - Lenient parser (`isLenient = true`) so trailing whitespace / BOM
      / non-standard JSON variants from upstream LLM SDKs don't blow up
      the parse.
    - GradumChatSession no longer needs the per-line try-catch — its
      `.collect` body assumes every emission is a JsonObject, and the
      outer `.catch` now handles connection-level failures only (which
      is the correct separation of concerns). The unused `eventJson`
      field is removed.
    
    Behavioural table:
      Old: Flow<String> + consumer per-line try-catch (skipped bad lines)
      New: Flow<JsonObject> + client per-line try-catch (skipped bad lines)
      Result: identical from the UI's point of view; the bad-line
      handling is now structural rather than conventional.
